# 摄像头与局域网接入

平台启动后监听 `0.0.0.0:8096`。当前采集主机在同一 WiFi 下的地址为
`http://192.168.1.129:8096`，浏览器访问“现场监控”即可调用后端统一输出的
MJPEG 画面，不需要在 USB 摄像头中安装程序。

## 当前自动发现

- Insta360 Link 2C：`/dev/video0`
- USB Composite Camera：`/dev/video2`
- USB Webcam：`/dev/video5`

`/dev/video1`、`/dev/video3`、`/dev/video6` 是 metadata 节点，不是重复的画面。
`/dev/ttyACM0` 是串口控制/身份通道，串口本身不能传输实时视频。

## RTSP / HTTP 网络相机

将网络相机写入 `config/network_cameras.json`，重启平台后会和 USB 相机一起出现在
摄像头墙。示例：

```json
[
  {"name": "工位4俯视", "url": "rtsp://camera-user:camera-password@192.168.1.50:554/stream1"}
]
```

也可在启动前设置环境变量，多路地址用分号分隔：

```bash
export SOP_NETWORK_CAMERA_URLS='rtsp://192.168.1.50/stream1;http://192.168.1.51/mjpeg'
```

生产环境应给网络相机做 DHCP 地址保留，账号密码放在仅部署主机可读的环境文件中，
不要提交到 GitHub。相机 VLAN、主机防火墙和浏览器客户端必须允许访问 TCP 8096。

## 低延迟流算法

实时管线使用两个独立线程：采集线程持续读 UVC/RTSP，推理线程只消费“当前最新帧”。
两者之间是容量为 1 的最新帧邮箱，而不是不断增长的 FIFO 队列。推理忙时，新帧覆盖
尚未处理的旧帧，因此空间复杂度保持 `O(1)`，画面不会随着运行时间越来越旧。

多相机共享一个有界 GPU 推理信号量，默认同一时刻只允许一路进入 GPU。这样可避免多套
模型同时争抢显存导致所有视频一起卡住。每个 MJPEG 客户端只读取已经编码的最新 JPEG；
局域网中某个慢客户端写超时后会断开，不会阻塞采集和推理线程。

网页显示以下诊断指标：

- 采集/显示 FPS：前者是相机实际输入，后者是模型处理后输出。
- 端到端/推理：前者包含等待、推理、画框、缩放和 JPEG 编码，后者仅计算模型推理。
- 过期帧：为了保持最新画面而主动覆盖的帧数；持续增长是允许跳帧的结果，不是队列泄漏。
- 缓冲策略：正常应显示“最新帧 0/1”或“最新帧 1/1”，绝不能超过 1。

可通过环境变量调节：

```bash
export SOP_CAMERA_MAX_FPS=12
export SOP_CAMERA_STREAM_WIDTH=960
export SOP_CAMERA_JPEG_QUALITY=68
export SOP_CAMERA_GPU_CONCURRENCY=1
export SOP_CAMERA_WIDTH=1280
export SOP_CAMERA_HEIGHT=720
export SOP_CAMERA_CAPTURE_FPS_0=30
```

如果端到端 P95 过高，依次降低 `SOP_CAMERA_STREAM_WIDTH`、模型 `imgsz` 或显示 FPS。
只有显存和 GPU 利用率有余量时才把 `SOP_CAMERA_GPU_CONCURRENCY` 增加到 2。USB 相机应优先
配置 `/dev/v4l/by-id/...-video-index0` 稳定路径，避免重启后 `/dev/videoN` 编号变化。

运行可重复延迟检查：

```bash
python qa/benchmark_camera_latency.py --url http://127.0.0.1:8096 --camera 0 --seconds 15 --start --stop
```

该测试只验证队列有界和视频链路延迟，不验证模型检测精度。
