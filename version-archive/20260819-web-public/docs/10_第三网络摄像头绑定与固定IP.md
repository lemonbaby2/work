# 第三网络摄像头绑定说明

## 已核实身份

截图中的第三摄像头已经完成身份登记，但还没有完成可用视频流绑定：

```text
名称：镭威视电池智链摄像机
IP：192.168.1.135
MAC：c4:3c:b0:be:40:e8
网关：192.168.1.1
DNS：192.168.1.1
子网掩码：255.255.255.0
协议：RTSP
平台编号：camera 2
```

设备 App/说明书同时显示摄像头自身 AP 配置网段：

```text
摄像头 AP 地址：192.168.188.2
子网掩码：255.255.255.0
AP 网关：192.168.188.1
记录的设备 WLAN：IPC-631180002304
```

这两个地址属于不同阶段：`192.168.188.2` 用于手机/电脑临时连摄像头热点并完成配网；摄像头加入工厂 Wi-Fi 后，平台应访问路由器 DHCP 静态租约中的 `192.168.1.135`。不能把 `192.168.188.2` 和工厂 LAN 的 `.135` 同时当作同一网段地址。

当前 Ubuntu 主机可发现该设备，TCP 554 端口曾成功开放，RTSP 服务标识为 `Hopeway RealServer/V1.0`。常见的海康/大华路径没有返回有效 SDP，因此平台不会伪造 RTSP 路径。

## MAC 与 IP 怎么固定

推荐两者同时使用，但职责不同：

- IP 是访问地址，网页和视频服务通过 `192.168.1.135` 访问。
- MAC 是设备身份，绑定时用来确认不会把另一台摄像头误接入。
- 最稳妥的固定方式是在路由器 `192.168.1.1` 中建立 DHCP 静态租约：MAC `c4:3c:b0:be:40:e8` 固定分配 IP `192.168.1.135`。
- 如果设备 App 已经设置为手工静态 IP，也要确保路由器 DHCP 地址池不包含 `.135`，避免 IP 冲突。

## 页面操作

进入“现场监控”页，在“网络摄像头 3 绑定”区域：

1. 保持 IP、MAC、网关、DNS和掩码为现场参数。
2. 从摄像头 App 的“分享/局域网/RTSP”页面复制完整流地址，填入 RTSP 地址。
3. 点击“测试 RTSP”，测试返回视频流信息后再点击“保存绑定”。
4. 相机选择器选择“网络摄像头3 · 192.168.1.135”，点击“启动实时检测”。

当前默认地址 `rtsp://192.168.1.135:554/` 只是占位地址，不能代表实际视频流；必须填写厂家实际路径和必要的用户名/密码。

页面还提供“自动探测候选路径”：它只会检查 TCP 554 和有限的常见 RTSP 路径，不会暴力破解账号，也不会把密码保存到配置或日志。若所有候选均返回 400，按 BTACAM App 流程先连接摄像头 AP `192.168.188.2`，把设备加入目标工厂 Wi-Fi，再从 App 的播放/分享页面复制完整 RTSP 地址。

## 启动失败时的固定排查顺序

平台现在会先检查 `192.168.1.135:554` 的 TCP 可达性，再检查 RTSP 视频流。若页面提示“网络不可达”或 Linux 返回 `No route to host`，这不是模型问题：请先让摄像头上电并连接到与 DGX 相同的 `192.168.1.x/24` 网络，再在路由器中按 MAC `c4:3c:b0:be:40:e8` 建立 DHCP 静态租约。

设备恢复在线后，在项目目录执行：

```bash
./.venv/bin/python scripts/probe_network_camera.py 'rtsp://用户名:密码@192.168.1.135:554/厂家实际路径'
```

探测必须同时返回 `tcp_reachable: true` 和 `ok: true`。然后把同一个完整地址粘贴到网页，先点击“测试 RTSP”，通过后再保存绑定。根地址不能启动检测。

临时不改配置文件时，也可以在 DGX 启动前设置：

```bash
export SOP_CAMERA_SOURCE_2='rtsp://用户名:密码@192.168.1.135:554/厂家实际路径'
./启动SOP平台_DGX.sh
```

启动服务默认使用 FFmpeg TCP RTSP、单帧缓冲；若现场设备只支持 UDP，可设置 `SOP_RTSP_TRANSPORT=udp` 后重启服务。
